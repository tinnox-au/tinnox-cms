# AGENTS.md

TINNOX CMS: a digital signage CMS in an npm-workspaces TypeScript monorepo (Fastify API in `apps/api`, React portal in `apps/portal`, Chrome player in `apps/player-web`, media worker in `apps/media-worker`, shared code in `packages/*`, SQL migrations in `db/migrations`, PostgreSQL 17 with row-level security). Architecture and decisions are in `docs/prototype-m0.md`, `docs/decisions-2026-11.md` and `docs/security/`. Repo-local agent skills are in `.agents/skills/`.

## Code Review Rules

`.cursor/BUGBOT.md` is generated from this section by `npm run check:docs -- --write`; `npm run check:docs` fails when they differ. Edit `AGENTS.md` only, and keep every rule in this one file: no nested or override rule files.

Report findings as Critical, High, Medium, Low or Observation. Cite `path:line` for every finding. Say what you could not verify by reading alone and mark it "unverified pending runtime". Check `docs/decisions-2026-11.md`, `docs/security/control-matrix.md` and earlier rounds under `docs/reviews/` first: a known, documented residual is reported as such, not as a new finding.

### 1. Three database roles

The roles are created in `infra/postgres/init/01-roles.sh`.

- `tinnox_app` is the only runtime role. It has no superuser, no `BYPASSRLS` and owns nothing. Flag any runtime code that connects as another role, any grant that lets `tinnox_app` own, alter or bypass RLS on a table, and any widening of its grants beyond what a feature needs.
- `tinnox_migrator` owns the schema. Only offline tools connect as it: the migration runner (`packages/db/src/migrate.ts`, also the test reset), the development seed (`scripts/seed.ts`) and TINNOX's provisioning script (`scripts/provision-member.ts`, from a controlled host); each connects through `connectMigrator`, which refuses any other role. Integration test helpers also connect as it, with plain clients, to arrange data (`TEST_DATABASE_MIGRATOR_URL`); that is test code, outside this rule. The e2e setup uses it only through the runner, the test reset and the seed. Its credentials, and the provisioning reader secret, never reach the API, the media worker or the player. The database administrator runs the incident scripts `scripts/revoke-all-sessions.sql` and `scripts/revoke-subject-sessions.sql`, as the superuser or `tinnox_migrator`; they work only under `SET LOCAL ROLE tinnox_definer`, which `tinnox_app` cannot take.
- `tinnox_definer` cannot log in, has `BYPASSRLS`, and only owns the narrow `sec.*` `SECURITY DEFINER` functions that must read before the organisation is known (session, device token, pairing, e-mail alerts). Every new or changed `sec.*` function must pin `search_path`, take only what it needs, return the minimum, and be granted `EXECUTE` to `tinnox_app` only. Migration 0013 grants it `UPDATE (first_signed_in_at, sessions_valid_after)` on `membership`, which its `sec.*` functions write. It also grants a read of `member_invite` and `UPDATE (status)` on it. Only `provision-member` uses these, under `SET LOCAL ROLE tinnox_definer`; no `sec.*` function does. Migration 0014 adds `sec.display_alert_orgs()`, which returns organisation ids only, for the alert check that runs with no session, and `sec.alert_recipient_by_token_hash(bytea)`, which returns the organisation and recipient id of an unexpired, unconfirmed alert address for a confirmation link, never the address; it grants `tinnox_definer` `SELECT` on five `alert_recipient` columns, not `email`. A new cross-organisation read is High until justified.

### 2. Tenant isolation

- A tenant statement runs on an `OrgTx` (`packages/db/src/tx.ts`): the handle of `changeOrg` (`packages/db/src/change.ts`), which sets `app.org_id` for that transaction only, or the one `enterOrg` returns inside `changePreOrg`; a read runs on the `OrgReadTx` of `readOrg`, a `READ ONLY` transaction. The handle of `changePreOrg` before `enterOrg` is a `PreOrgTx`: it has no `query` and goes only to the `sec.*` wrappers. `withOrg` and `withResolvedOrg`, on which `changeOrg` and `changePreOrg` are built, and `withoutOrg` are for tests only (`@tinnox/db/testing`). The type checker holds this: the API holds no pool, only the `Database` of `createDatabase()` (`AppContext.db`), which has no `query`. `tinnox/no-query-off-transaction` holds `poolAsTx` in the API and the migrator's pool in the scripts; the alert check's session lock is taken only through `withSessionLock` (`packages/db/src/session-lock.ts`), and session advisory-lock SQL is refused outside `packages/db/src`. Lint keeps `poolAsTx` and the `sec.*` wrappers that work across organisations (`CROSS_ORG_WRAPPERS`) to the files of `UNSCOPED_HELPER_FILES` (`eslint.config.js`). It also refuses SQL text in the API and the scripts that sets `app.org_id` or begins or ends a transaction: `tinnox_app` may set any `app.org_id`, so that lint is all that holds such text. Flag what they do not see: a tenant statement on anything but an `OrgTx` or `OrgReadTx` inside `packages/db/src`, where that lint does not run; such SQL text built at run time, named by a parameter (`set_config($1, $2, true)`), kept in a variable in lower case (or a bare `COMMIT` in one not named in capitals), behind a SQL comment or in a `DO` block; and a new file in `UNSCOPED_HELPER_FILES` whose reason does not hold.
- The organisation is an `OrgId`. In the API, only the lookups of `packages/db/src/sec.ts` return one: the organisation of the verified session membership, of the device credential, or of another row the database itself named (a completed pairing, a media job, a confirmation link, the alert check's list). The offline tools also have `newOrgId` for an organisation being created and the `org_id` of a row read through `asDefiner` (both from `@tinnox/db/migrate`), and tests have `testOrgId` (`@tinnox/db/testing`). `readOrg`, `changeOrg` and `enterOrg` take nothing else, so a value from a path, query, body or header does not compile there. Lint refuses a cast to `OrgId` itself, a type predicate for it, an `OrgId` written in the type arguments of a call (`query<{ org_id: OrgId }>`) and one in the annotated type of a query result (`const r: QueryResult<{ org_id: OrgId }>`). Flag what neither sees: a new lookup that returns an `OrgId` for a value the caller chose; a cast to `never`, to an alias of `OrgId` (`type Alias = OrgId`, then `as Alias`), to a named type that contains one, or to a type derived from one (`as typeof org`, an indexed access, `ReturnType` or `Parameters`); the type arguments of a constructor (`new Box<OrgId>()`); an overload signature that returns `OrgId` over a body that returns a string, and a string written into an `OrgId` array or field through a wider alias; a named row type with an `OrgId` field given to `query` (`interface Row { org_id: OrgId }`, then `query<Row>`); a generic helper whose `as T` is inferred as `OrgId` (`const id: OrgId = brand(value)`); and, in the offline tools, `newOrgId` for an organisation that already exists or an `org_id` read through `asDefiner` that is not the row's own column. The casts to the other brands (`OrgTx`, `SqlFragment`, `PlannedPublication`, `WritePermit` and the rest) leave the same derived-type and constructor forms, and a generic helper given the brand as its type argument (`brand<SqlFragment>(raw)`).
- Another organisation's id gets exactly the answer an id that was never issued gets: 404 where the lookup finds no row (DEC-35), never an answer that only an existing row could cause. A 403 is decided without looking up the requested id, so it is the same for an own, unknown or another organisation's id: the role guard and `assertStillAllowed` (DEC-35), the origin and CSRF checks, the signed media URL checks and the heartbeat's refusal of a `displayId` other than the credential's (`docs/player-protocol-v1.md` section 10). The one exception is the people routes' rank, self and grant rules (`docs/portal-v2/stage-c.md` section 1.6): they may be decided after the target is read under row-level security, so another organisation's id still answers 404 there. Lint refuses a 403 built outside `apps/api/src/auth/`, an error status set on the reply, and a role refusal imported outside `apps/api/src/auth/` but by the two files of `ROUTE_REFUSAL_IMPORTERS` (`eslint.config.js`): those rules and the unreachable unknown-role check of `apps/api/src/routes/audit.ts`. Flag what it does not see: a 403 code held in a variable (also one a subclass's constructor passes to `super`), an error status on the reply held in a variable or chosen by a condition (`reply.code(ok ? 200 : 403)`), `HttpError` reached through a namespace, a variable or `Reflect.construct`, and a refusal of `apps/api/src/auth/` called after reading the caller's own row, which `tests/integration/cross-org.test.ts` cannot tell apart, since neither of its ids finds a row. Each new table or route gets a case in `packages/db/test/rls.integration.test.ts` or `tests/integration/cross-org.test.ts`.
- Media, signed URLs, publications and player endpoints are tenant data too: check that a signed URL or device token for one organisation cannot reach another's objects.

### 3. Audit record in the same transaction as the change

- Three things write an `audit_event` row (D3): every successful change to tenant or security state; every attempt, whatever its result, at sign-in, pairing, revocation, upload and publishing; and authentication and authorisation refusals (CSRF, role, device credential, pairing code), thresholded as they are today. Other business-rule refusals (in-use 409s, edit 400s, 404s), heartbeats, purges, session activity, login state and counters under their threshold write none. Whether a new kind of event is security-relevant is the reviewer's call. The change returns the row as `{ value, audit }`, and `changeOrg` or `changePreOrg` (`packages/db/src/change.ts`, under `changeAsOperator`, `changeAsDevice`, `changeAsJob` and `changeOrgAsMigrator`) writes it on the change's own transaction before `COMMIT`, so both commit or neither does. Writing the change in one transaction and the audit in a later one is a finding (see CX-01 in `docs/reviews/2026-11-16-backend-round-1/`). Two exceptions, both refusals where nothing changed: `auditStandalone` (unscoped sign-in and device-credential refusals) and the scoped refusal-only transaction, `recordRefusal` (`apps/api/src/auth/refusal.ts`; SCR-32) (D2). Three writes are kept as built at step 20 of the adoption plan, open on status card CMS-36, and commit no row: `alert_closed_silently`, `pairing_expired_by_time` and `development_seed` (`UNAUDITED_REASONS`); so, also open, does a pairing request refused as rate-limited (429) or after five code collisions (503) (`apps/api/src/routes/player.ts`); report them as known residuals. Provisioning's invite expiry writes its own rows in SQL (`auditedInSql`, D25).
- Audit rows never contain content, secrets, tokens, signed URLs or query strings. `occurred_at` is set by the database, so code must not pass a time.
- `audit_event` is append-only. Flag any `UPDATE` or `DELETE` on it and any change to its trigger.

### 4. Migration history

- Migrations live in `db/migrations/NNNN_description.sql`, are applied in order, and each runs in one transaction with its `schema_migrations` row. A migration that has been merged to `main` is never edited, renamed or deleted: `npm run check:migrations` fails such a change in CI (against `origin/main` on a branch or pull request, against the first-parent history of `HEAD` on `main`), and the runner rejects a changed checksum on any database that applied it. Fixes go in a new migration with the next number.
- Flag a migration that depends on data only present in development, and non-transactional statements (`CREATE INDEX CONCURRENTLY`, `VACUUM`) that cannot run inside the runner's transaction.
- Ownership changes on `sec.*` functions use `SET LOCAL ROLE tinnox_definer` and `RESET ROLE`, as in migrations 0003, 0004, 0010, 0012, 0013, 0014 and 0015.
- Locks: flag table rewrites or long `ACCESS EXCLUSIVE` locks on large tables. `tinnox_migrator` has `lock_timeout = '30s'`.
- Each migration that changes tables, policies, grants or functions has an integration test like `packages/db/test/migration-0005.integration.test.ts` when it upgrades existing data.
